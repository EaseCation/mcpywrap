## 新增场景与结果

新增行为测试位于 `tests/test_lifecycle_races.py`。先运行修复前版本保存失败，再修改服务层并回归；Windows 的修复前日志保存在 `test/lifecycle-audit-round2`，Mac 也独立复现了主要失败。

| 假设/场景 | 观察结果 | 修正或保留的规则 |
|---|---|---|
| 系统未能创建 worker，GUI 进程仍活着 | 原记录继续是 starting，仍被算作占用 | 记录明确失败及实例状态，返回会话 ID，不保留虚假 starter 占用 |
| 装配期间用户停止启动 | 原 Windows 服务仍调用游戏启动器 | Windows/native 在真正启动前共用取消检查，取消后恢复本次准备 |
| stop 等待 worker 时，worker 才发布游戏 PID | 原 stop 会漏掉该游戏并报告 exited | worker 结束后重新读取身份并处理新记录的游戏 |
| worker 在记录游戏身份前崩溃 | 原 stop 宣称退出，但占用仍不能安全释放 | 明确返回 recovery_required，不伪造退出确认，不删占用记录 |
| 增量发布后，其他程序修改运行文件 | 原回滚覆盖后来的外部内容 | 恢复前核对旧/新版本指纹，未知改动保留并报告 |
| 外部程序新增一个空目录 | 原回滚会清理该目录 | 核对完整目录清单，目录本身也是要保留的内容；覆盖只有目录变化的发布 |
| 用户在发布后修改实例配置 | 原回滚先恢复文件，再发现配置冲突 | 先检查配置与内容，再做任何恢复变更 |
| 装配期间 common 的依赖声明改变 | 原检查只覆盖主项目，未拒绝过期依赖图 | 把所有参与项目的依赖声明纳入指纹，变化时发布前拒绝 |
| 活动部署中的文件变成同名目录 | 原实现尝试增量替换，后续恢复容易混淆类型 | 预先识别文件/目录类型变化，要求停止相关实例后重启 |
| 持有真实 OS 锁的进程退出 | 退出前另一进程不能获得锁；退出后可获得 | 通过；不依赖删除残留锁文件 |
| 两个调用方同时启动同一世界 | 第二个调用方被串行化保护阻挡，只创建一个会话 | 通过；CLI/Qt 共享服务边界 |
| 更新只授权一个读者，但另一个世界也在读取部署 | 未授权读者存在时不写文件；显式纳入所有读者才更新 | 通过；不静默扩大影响范围 |
| 普通源文件在装配期间发生变化 | 发布前拒绝，旧产物不变 | 通过；与新增的传递声明检测共同覆盖输入变化 |
| 第二个调用方等待已有启动超时 | 原逻辑会写 stop，取消并非它创建的会话 | 只有持有本次新建 worker 的调用方可在超时时取消；观察者只报告超时 |
| macOS 失败历史会话的 PID 被其他进程复用 | 原后端将 PID 复用异常当作阻挡，不能继续运行 | 改用共同占用判定，旧 PID 已复用即不再代表原会话存活，不操作新进程 |
| macOS 接管仍在启动中的已有 worker | 原逻辑直接交接尚无 game 身份的记录 | 等待启动完成后再交接，不重复创建世界/进程 |

上述共 17 个测试，包含 Windows/native 取消边界各一项。12 个修复前失败场景已修正；新检查集中于会话、占用及部署服务，没有给 CLI 和 UI 添加独立启动分支。

保留的限制：游戏身份根本没有记录时，无法凭“worker 已退出”证明游戏不存在。此时拒绝恢复是必要保护，本轮修正的是错误的成功报告，不通过清锁掩盖未知状态。

## 正式 Mod 入口问题的定位

先排除了 `PYTHONPATH`：去掉它后仍没有自动加载入口。随后读取实际游戏模块注册表，确认加载器在 `common.minecraftMod`，并观察其 `LoadWindowsAddonPy` 路径处理。

在 Windows 引擎 **3.10.0.420447** 中，该函数按固定层数截取绝对脚本路径。使用引擎自己的函数和只记录调用参数的接收器，得到以下结果；没有修改引擎函数或注入业务模块：

| 输入路径形状 | 引擎生成的模块名 |
|---|---|
| `C:/Users/Test/AppData/Roaming/.../behavior_packs/pack/AuditMain/modMain.py` | `AuditMain.modMain` |
| 上轮深层隔离资料目录下的相同文件 | `com.netease.behavior_packs.pack.AuditMain.modMain` |
| `D:/mcpy-audit/profile/AppData/Roaming/.../behavior_packs/pack/AuditMain/modMain.py` | `AuditMain.modMain` |

证据：`test/lifecycle-audit-round2/live/03-loader-contract.json`、`04-path-contract.json`、`05-path-transform.json`。

随后保留同一个世界、相同脚本和资料，只使用浅层目录别名。引擎自动执行了客户端和服务端初始化，日志出现 `[LifecycleAudit] client=absent`、`server=absent`，公开 Python 查询读到真实初始化结果。这修正了上一轮的归因：**导入失败来自隔离路径与该引擎规则的不兼容，不能归因于装配目录或全局链接名称。** 上轮 UUID 命名候选已经撤回。

验收脚本现在会为过深的测试资料路径创建临时兼容别名，数据仍留在测试输出目录；本次拥有的游戏全部停止后才移除自己创建的别名，不改个人资料或全局包。生产客机收到的网络包是否经过相同路径分支，需要另做正式入口验收，不能由这个本地加载器实验推定。
