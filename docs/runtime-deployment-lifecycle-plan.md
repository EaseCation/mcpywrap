# 运行部署生命周期重构计划

状态：经过兼容性反例审查的设计建议，尚未实施运行时代码改动。调研日期：2026-10-15；代码基线：`b6cc3f0`。先通过兼容性原型门槛，再冻结生产设计。

目标是用一条可恢复的部署流程替换现有分散逻辑，解决依赖变化、实例选择、共享目录、全局链接和启动状态之间的不一致。默认开发实例保留世界数据，每次重新启动运行当前项目代码；历史代码复现不属于本次功能。**不能通过默认禁止所有多开、丢失源码文件或悄悄收缩热更来简化实现。** 详细反例见 [兼容性与副作用审查](runtime-deployment-compatibility-review.md)，场景优先级与取舍依据见 [MCDK 竞品与产品分析](mcdk-product-tradeoffs.md)。

产品优先级为：数据与加载正确性、日常修改到验证的反馈效率、既有受支持场景、最后才是历史代码复现。多开分为同版独立世界、主机加联机客户端、不同版本 A/B；不能仅按进程数量制定限制。部署内部模型不作为用户每次运行必须学习的概念。

## 2. 建议确定的产品规则

1. **实例拥有世界，会话拥有一次运行，部署描述供引擎读取的代码和资源。** 三者不再通过一个 cppconfig 文件隐式混为一体。
2. `run` 保留“最新创建实例”的排序，在成功进入过世界的可用实例中选择，部署当前代码；不改成“最近使用”。失败的新建记录可见、可显式重试，但不自动成为默认实例。
3. `run --new` 只创建新世界，不承诺保存旧依赖组合，也不绕过运行占用检查。
4. Windows 优先验证**同一部署可被多个不同世界读取，活动部署不得被普通启动替换**。同一世界重复 run 校验请求参数后复用，明确 `already_running=true`、未重新部署；另一世界或 `--new` 在当前输入与活动产物一致时可直接加入，不重建目录/链接。代码已变化则返回 `deployment_in_use`，不偷用旧代码。启动中重复请求等待原请求或给出明确未完成结果，禁止重复创建游戏，也不能把缺少 game 信息的记录直接传给旧 handoff。
5. 多个世界可长期共存；保留同版并行能力是验收要求。不同项目可同时运行，前提是全局包关系兼容。macOS 保留实例独立部署和并行能力。**实际世界路径始终只能有一个活动写入者**，跨项目复制的相同世界引用也受此约束。
6. 显式 `runtime reload/watch` 是允许修改活动部署的入口；依赖图、包身份、目录布局或引擎变化必须重启。多会话共享产物时的定向热更尚需原型验证，不能把仅向一个进程发送 reload 误当作文件隔离，也不能静默广播。无依赖源码直读的开发体验差异须在兼容性阶段验证与处理。
7. `remove` 继续只更新声明和锁文件。下次 run 重新解析并装配，不在依赖编辑时删除链接、改动世界或停止游戏。
8. 快速热更与无变化复用是核心交付要求。保留显式 watch/reload，GUI 可提供可见的“运行并监控”组合动作；不引入隐藏监控或大量运行模式。资源更新粒度按能力区分。
9. 主机加多个联机客户端单独验收；已有 connect 不自动等于完整的 MCDK Sub 客户端工作流。加入客户端不能部署/重置宿主。不同版本同时 A/B 在真正隔离之前不作为 `--new` 的承诺。

第 4 项是最低候选模型，不代表多实例隔离已经证明可行。需要同时保留不同代码并行或多实例分别热更时，先研究 Windows 引擎数据根目录隔离；现有 open_game 尚无该接口，不能凭空假设参数可用。单项目单会话会削减功能，已从默认建议中撤回。不同目录保留相同 UUID 且仍使用同一全局数据根不能解决隔离；重写 UUID 也不能作为快捷替代。

共享部署有多个读者时，首版可对冲突写入实行明确保护，但必须披露其对旧热更工作流的影响，并用实际联调样例决定是否需要同时交付显式共享更新。不能用静默广播弥补定向热更缺少隔离。保护冲突写入不等于限制所有游戏进程。

## 3. 模型与代码边界

沿用现有 `GameBackend`、`DependencyService`、`AddonProjectBuilder`、session worker 和 `checked_process()`，不增加第二套后端框架、事件总线或通用工作流系统。

建议新增一个小型 `mcpywrap/runtime/` 包，职责按数据归属拆分：

| 模块 | 唯一职责 | 不承担的工作 |
| --- | --- | --- |
| `instances.py` | 实例记录、选择、唯一前缀匹配、默认实例规则、旧记录导入 | 构建、全局链接、进程启动 |
| `deployment.py` | 解析后的部署计划、暂存、提交/恢复日志、占用与版本校验 | CLI/Qt 展示、世界数据库修改 |
| `lifecycle.py` | 选择→预留→部署→启动→确认→结束的编排 | 平台路径发现、引擎启动细节 |
| `utils/locks.py` | 跨平台内核文件锁和线程互斥的统一入口 | RemoteError、会话/服务业务规则 |

小型数据结构放在所属模块，避免大量单类文件。Windows 的链接归属和低层目录操作继续放在 `mcstudio/symlinks.py`；平台差异由后端返回部署位置、占用范围、启动配置及就绪信号，业务代码不散布 `sys.platform` 分支。

依赖方向应为：CLI/Qt → lifecycle → deployment/instances/backend → builder、文件系统与引擎。删除 backend 反向导入 `commands.run_cmd` 的关系。构建器只生产产物，不决定实例、链接或启动。

### 最少持久化信息

- **实例**：`schema_version`、`level_id`、项目归属、backend、世界/配方位置、`created_at`、`last_ready_at`、最近启动尝试 ID。失败详情引用 session，避免多处复制可变状态。
- **部署**：项目身份、规范化项目路径、部署 ID、依赖与布局指纹、产物摘要、包种类/UUID/路径映射、当前占用会话集合、更新序号。链接的发布者和使用者分开记录，以保留相同物理包目标的合法共享。
- **会话**：沿用 session.json，增加 deployment ID、启动阶段、结构化错误、就绪时间和预留令牌；复用现有 PID + 创建时间 + executable 身份检查。
- **全局归属表**：以实际引擎全局数据根目录为作用域，记录链接路径、种类、UUID、目标路径、项目身份、部署 ID 和占用会话定位信息。
- **事务日志**：每次部署保存必要的旧值、暂存/备份位置、已经执行的步骤和事务 ID；未完成的日志用于下一次命令恢复。

不保存完整依赖历史。部署 ID/摘要是诊断与一致性信息，不承诺其产物永久不可变：显式热更会增加更新序号并刷新内容摘要；结构指纹保持不变。

项目身份保存在不入 Git 的运行元数据中，并绑定规范化根路径。复制/移动整个项目后不能仅凭复制来的 ID 接管链接；路径不匹配应重新认领或明确迁移。UUID、包名、目录名均不能单独证明归属。

### 目录选择

在共享同版候选模型中，Windows 保留 `.mcpy/runtime/assembled` 作为唯一活动运行产物位置，避免再引入一轮必然的路径迁移；若独立数据根原型证明需要改为实例隔离，再一次性确定布局，不能同时保留两套生产启动流程。源码、build/package 产物、编辑器产物不与游戏部署复用。build/dev 的用户自定义输出也不得绕过受管路径保护。

实例 cppconfig 暂保留 `.runtime/<level_id>.cppconfig`，新增实例元数据放 `.runtime/instances/<level_id>.json`；世界数据库保留原位置。部署信息放 `.runtime/deployment.json`，事务资料放 `.runtime/transactions/<transaction_id>/`。macOS 保留现有实例目录和世界位置，通过相同服务管理。

这些路径统一由一个布局对象产生，业务层不拼散落的字符串。暂存和备份应与被替换目录同卷。全局归属表和锁放在已发现的全局数据根下的工具专用子目录，不硬编码 APPDATA、盘符或引擎版本。

运行产物内部包路径也应按种类稳定映射；主项目修改源包文件夹名称不能再次造成路径切换。复用 builder 的目标包映射能力，集中定义行为包/资源包布局。全局受管链接名由项目身份与包种类/身份产生，不依赖可修改的显示名称。

## 4. 唯一启动流程及锁边界

```text
校验请求、发现引擎和资源（不写部署）
  → 在项目锁内恢复遗留事务、选择实例、检查活动占用、预留启动
  → 启动 worker；交接预留令牌
  → worker 校验令牌与占用，解析依赖一次，生成暂存产物
  → 在部署锁与全局链接锁内重新校验、写恢复日志、发布目录/链接/配置
  → 启动游戏并立即记录进程身份，建立会话占用
  → 进程和控制通道可用：running
  → 引擎明确进入世界：world_ready，更新实例 last_ready_at，完成事务
  → 游戏确认退出：释放占用，保留世界和部署诊断
```

父进程只进行请求校验、选择和预留，不装配。worker 是本次启动事务的执行者，消费固定的请求和部署计划，不再自行决定另一套运行目录。

必要约束：

- 使用真实跨进程锁，不能只靠先查询再启动或进程内 threading.Lock。抽出当前 `directory_lock` 的底层实现，错误类型与“服务运行”文案从通用锁中移除；同进程多线程还要统一互斥。
- 项目锁保护实例选择和启动预留。占用范围 Windows 为项目，macOS 为实例。锁顺序固定为项目/实例部署锁 → 全局链接锁；任何路径不得反向获取。
- 父进程释放锁后再等待 worker；worker 校验持久化预留令牌。不能让父进程持锁等待、worker 又等待同一把锁。
- “starting 且 worker 还没有写 PID”的短窗口由启动方身份和预留记录覆盖，不能直接当作失败、释放占用。
- 全局锁只覆盖全局冲突复查、发布/恢复和启动身份交接所需阶段，不覆盖完整构建、游戏就绪等待或游戏整个生命周期；跨项目由占用记录协调。
- 操作系统锁解决并发修改，持久化占用记录解决进程死亡后的归属；两者不可互相替代。
- 同版第二个世界加入只增加读取占用并准备自己的实例配置，不进入现有部署的替换事务；它失败时不得恢复或删除第一会话正在使用的目录/链接。实际世界存储路径另有独占占用，不能仅用项目锁防止重复打开世界数据库。
- worker 崩溃但游戏存活时必须保留占用。PID 身份无法核实时返回可诊断的 busy/recovery_required，而不是根据过期时间删除记录。
- Spawn 成功但游戏身份尚未保存是明确的崩溃窗口。提交日志必须先记 `spawning`，失败恢复时按启动配置/进程身份核查；不能确认游戏已退出则冻结该部署，不能自动回滚或再启动。是否利用 Windows suspended launch 缩小窗口，留给原型验证，不作为未经验证的前提。
- 启动超时只请求取消；收到超时不等于游戏已退出，不立即清链接、释放占用或将世界当作可重启。

依赖只解析一次：让 builder 接收已经校验的装配输入，沿用现有合并算法。先修复兼容性探针发现的过滤错误、目录遗漏和布局不稳定，校验 Python 编码/行号变化，不能直接把现有 builder 扩大到所有项目。暂存产物携带输入指纹；检查声明、锁文件及参与文件的一致性。检测到构建中变化则放弃暂存并提示重试，不发布无法说明来源的混合产物；不能宣称无文件系统快照时可原子捕获任意外部写入。

性能与空间是部署正确性的一部分：无变化的运行输入应复用已验证部署，测量大项目构建/哈希/备份成本；准备阶段与引擎启动阶段分别计时，不能让新增的完整装配消耗原本 30 秒的启动等待预算。保留取消、阶段进度和失败现场清理，不引入无界缓存。

## 5. 全局链接的归属与更新

在全局锁内先列出本次全部变更和冲突，再修改任何链接。UUID 冲突保护继续存在。

| 遇到的对象 | 处理 |
| --- | --- |
| 当前项目登记的链接，真实链接目标与记录一致，无占用 | 可更新目标或移除已不再需要的链接；写入事务前像 |
| 当前项目登记的链接，仍被会话使用 | 普通启动拒绝替换；绑定会话的内容热更走专用流程 |
| 其他项目的同 UUID、不同目标链接，无论是否闲置 | 报归属冲突，不自动接管 |
| 同 UUID、相同真实包目标，已有其他项目使用 | 保留可证明的共享引用，不据 project owner 不同一律拒绝；任何一方退出不清理其他引用 |
| 真实目录、手动安装包、归属未知的链接 | 保留原状，输出具体冲突位置与修复方式 |
| 登记目标与实际目标不一致，或登记文件损坏 | 视为外部修改，停止自动修复 |
| 已登记的失效链接 | 同样校验归属和占用后按事务处理；不能因为不存在就忽略 |

首次升级不能假设所有指向本项目目录的旧链接都是工具创建。增加一次性的旧状态导入：从旧 cppconfig、会话和精确链接目标列出候选；证据不足时提供明确的认领/解除链接操作，列出将操作的链接，不能通过 UUID 相同或名称相似自动删除。

旧依赖包的链接也要进入迁移清单；旧版可能直接链接了依赖源码，它们不一定处于主项目目录内。无法证明独占的共享依赖链接保持未受管。

所有更新重新确认 link/junction 类型和目标，仅操作链接本身。禁止递归穿越 junction，禁止删除同名真实目录。提权辅助进程必须执行同一事务协议并持有相同全局锁，不能保留一个绕过归属检查的旧写入口；无需权限时继续使用现有 junction 回退能力。

受管机制只协调新版工具。旧 CLI、手工操作和外部 MC Studio 不会遵守新锁；发现未知使用者或有争议的包时保守拒绝覆盖，并说明需要退出或认领的对象。不要宣称已获得对外部程序的强隔离。

竞品源码显示 MCDK 普通启动会清理同一数据根下的全局包目录，Sub 客户端启动则跳过这一步。与 MCDK 交替/同时使用是具体的共存场景，应在 P0 验证外部改写检测和恢复；若承诺并发互不干扰，必须先验证独立数据根，归属记录本身无法阻止外部清理。

## 6. 事务、成功标准和默认实例

采用少量明确阶段：`reserved → prepared → published → spawned → ready`。失败进入补偿恢复；恢复未完成则保留 `recovery_required`。这些是部署阶段，不额外复制一套 session 生命周期。

`running` 继续表示进程/通道就绪，避免改变现有 CLI 的返回约定；`world_ready` 表示引擎就绪信号已确认进入世界。它不等于所有 Mod 的业务验收成功。复用两端已经存在的 `backend.refresh()` 就绪检测，并对支持的引擎版本验证可靠性。

就绪日志缺失或用户进入菜单不能直接判为启动失败；保留 running/就绪未知的区别，不因为缺少 HUD 标记自动终止游戏。默认实例资格依赖可靠的初始化证据，须验证旧引擎和日志异常的恢复途径，避免把正常世界永久排除。

- `prepare_cppconfig()` 拆成不写磁盘的合成函数和原子写入函数。新建时世界设置进入预留请求；不先写空包列表的“正式实例”。
- 新 cppconfig、链接修改清单、产物和实例记录先准备在暂存区；发布前保留旧配置/归属/目录的恢复信息。
- **游戏未生成时失败**：恢复本次改动的目录、链接、配置和归属；失败尝试保留诊断，不成为默认实例。
- **游戏已生成后失败**：先确认游戏退出，再恢复工具管理的部署文件；无法退出则保留占用和现状，报告恢复待处理。
- 世界数据库不是事务回滚对象。游戏可能已经修改世界；不承诺恢复世界内容，不因启动失败自动删除残留存档。新世界部分生成时标明可显式重试。
- ready 后将部署视为提交，更新 `last_ready_at`；随后才清理恢复副本。清理失败是警告，保留位置，不反向伪装成游戏启动失败。
- 后续进程异常退出不抹除实例曾经成功进入世界的事实；失败详情属于本次会话。
- 检测到运行产物出现非构建清单文件或被引擎改写时，区分已验证的可再生缓存与未知用户数据；不能整树替换后静默删除未知内容，也不能自动反写源码。保留副本与冲突详情，纳入存储语义验收。
- 回滚也采用日志、幂等步骤与条件校验：只恢复仍属于本事务的路径，保留原始错误和回滚错误，不用一句“检查权限”覆盖。

新实例失败后再次普通 run：有成功实例则选择成功实例并提示前次新建失败；没有成功实例则明确报告失败实例 ID 和显式重试方式，不持续生成新失败世界。显式 `run <唯一前缀>` 重试保留创建设置；前缀不唯一必须报错。

旧实例没有 ready 记录时，使用真实世界文件和历史会话证据导入为 `legacy_existing` 或 `unverified`，不可伪造成功时间。存在真实世界的旧实例可作为迁移后的候选并提示其历史状态未验证；仅有 cppconfig 的记录不能自动成为默认实例。

## 7. 热更、编辑器、Map 与 macOS

**热更**：所有写入收口到 deployment 服务。先校验目标参数、会话身份、能力和结构指纹，再暂存内容差异；禁止先 build 再判断需要重启。影响装配的依赖声明/锁文件、UUID、manifest 结构、库挂载和包目录变化要求 `restart_required`，运行产物不变。按真实装配内容计算指纹，README 或无关工具配置变化不应阻塞。新增/删除文件不一律禁用，区分可部署的内容变化、需要引擎重新加载的资源和包结构变化，用旧新实机对照确定原有支持边界。

watch 只采集变更并提交给同一服务，不直接修改活动目录。删除 `watch → 独立构建 → deploy 再构建` 的双重流程；离线 dev/build 仍可复用通用 watcher，但写入运行部署必须经过协调器。内容发布使用逐文件暂存/替换和日志，不在活跃引擎下重命名整个包树。文件更新和引擎内存重载无法原子提交，失败或响应未知时标记需重启，不宣称已经回滚游戏内状态。

**GUI/编辑器**：GUI 刷新依赖改为只读 resolve/validate。编辑器需要产物时使用独立的 editor 工作目录，但必须验证 `EditAddOnPaths` 与 `SaveBackAddOnPath/SaveBackMapPath/EditPath` 的实际保存关系；独立目录本身不保证保存回源码正确，不把依赖合并结果整体反写主项目。编辑保存实机验收通过后才能冻结方案。所有游戏启动，包括人工前台和 Qt，都走 session worker，保留观察者与拥有者的退出区别。

**Map**：不将 Addon 的合并模型强套到 Map。为 Map 实现同一部署计划的适配器：保留多包语义，暂存运行包和 world pack 引用；首次世界复制单独记录，既有 db/level.dat 不重新复制。Map 自有包、依赖包、世界内链接和全局链接都受同一占用保护。不能保留 Map 调用旧 `_setup_dependencies()`/旧启动链作为长期例外。

**macOS**：复用生命周期和事务语义，保留实例独立装配、引擎版本固定和旧运行包协议适配。不为了 Windows 的共享限制降级 macOS 的隔离能力。启动装配和热更使用相同实例部署锁；修复提前写 instance.json、删除旧 packs 后再 rename、配置/启动失败不恢复等问题。真实失败恢复必须在 macOS 主机验证。

**网络模式**：继续只做目标与依赖校验，不部署本地世界资源，也不申请本地世界占用。共享 sessions 的改动必须覆盖网络回归。

## 8. 实施顺序与旧逻辑删除清单

每一阶段都是小范围、可验收的替换；中间提交可用于开发，但不发布新旧启动入口同时可写同一目录的版本。

| 阶段 | 交付及完成条件 | 同期删除/替换 |
| --- | --- | --- |
| P0 产品契约、兼容性与实机原型 | 用单人迭代、依赖修改、同版双世界、主机+客户端、编辑器保存样例固定预期；修复文件语义反例；验证 3.10/受支持 3.9 的反馈速度、更新范围、独立数据根可行性和外部工具共存；故障注入验证恢复 | 原型位于测试/调研目录，不引入生产开关；不能以单会话禁用代替并发验证，也不以安全为由忽略常用开发效率 |
| P1 状态与启动收口 | 实例元数据、统一选择、预留、结构化错误；CLI/Qt/前台统一 worker；重复启动测试通过 | `_get_all_instances/_get_latest_instance/_match_instance_by_prefix` 搬入新实例服务并替换；删除前台直接 `_run_game_with_instance` 分支 |
| P2 装配与部署事务 | 无依赖也装配；单次解析；归属登记、旧状态导入、链接差量提交与回滚；Windows Addon/Map 接通 | 删除 `_setup_dependencies` 条件装配和所有运行调用；拆掉 `_run_game_with_instance` 大函数；删除布尔返回掩盖错误链 |
| P3 封闭其他写入口 | GUI 只读依赖、editor 隔离、reload/watch 校验与统一写入；实例删除走同一占用检查 | 删除 WindowsBackend 回调 command 的导入；删除独立 watch 输出与重复 build；移除旧链接 helper 的独立决策逻辑 |
| P4 macOS 与发布验收 | 接入共同生命周期，补全失败恢复；Map、网络、认证和双平台契约回归；更新文档/技能 | 删除 macOS 重复选择/活动检查逻辑，保留必要的运行包协议适配；移除迁移外的旧文件扫描路径 |

`symlinks.py` 最终只保留受管链接操作、冲突检查及确有需要的权限适配。构建器保留已有合并规则和 Windows 短暂锁重试，但运行部署的备份必须由外层事务持有，不能在链接/启动尚未成功时被 builder 提前清理。可通过“build 到未发布目标”实现，不再复制一个运行专用构建器。

删除实例、clean-all 同样经过 lifecycle：活动检查、锁、世界路径核验、记录更新保持一致。`--force` 只跳过人工删除确认，不能跳过占用和路径保护。替换现有手写递归删除函数，统一安全区分目录、symlink 和 junction。

路径和策略集中配置；不加入 `legacy_mode`、`force_uuid`、`skip_conflict` 等兼容开关。旧状态导入是一次性边界，不是每次运行失败后回退旧逻辑。

## 9. 测试与发布门槛

| 场景 | 必须验证的结果 |
| --- | --- |
| 无依赖、首次增加、最后移除、更换/移除传递依赖 | 同一运行布局；实际文件和加载标记正确；旧文件不存在；无旧链接残留 |
| 无依赖时编辑源码 | 活动游戏产物不随源码直接变化；重新 run 或显式热更才更新 |
| 同世界重复 run、另一世界 run、run --new | 同世界参数匹配才复用；同版不同世界可并行且零重部署；变更已被占用的部署时拒绝且无副作用 |
| 两个 CLI 同时 run、Qt 与 CLI 竞争 | 同一世界只产生一个获准启动；不同世界按部署兼容性加入；不依赖测试进程内 mutex |
| 主机加多个联机客户端 | 各自控制/日志目标明确；加入不修改宿主世界与部署；网络能力不足时明确报告 |
| 不同项目、同名项目、复制项目、相同 UUID | 不抢占他人链接；独立且无冲突的项目能并行 |
| 改 UUID、源包目录名、项目显示名称、依赖包路径 | 按归属差量处理；路径规范化一致；运行期间拒绝结构变更 |
| GUI 刷新、edit、build、package、watch 与 run 同时发生 | 所有非运行操作不能隐式覆写活动部署 |
| 链接第 N 步失败、目录占用、cppconfig 写失败、Popen 失败 | 恢复原目录/链接/配置/登记；错误保留具体阶段与路径 |
| 启动后立即退出、ready 前失败、ready 超时 | failed/未验证状态准确；失败新实例不成为默认；世界不自动删除 |
| CLI 被杀、worker 被杀、游戏仍存活、PID 复用、身份拒绝访问 | 不释放错误占用、不强杀不相关进程、不覆盖可能被读取的目录 |
| 发布任一步骤崩溃、回滚中再次崩溃 | 下一次命令幂等恢复，或明确 recovery_required；保留恢复副本 |
| 旧配置、旧源码链接、旧 assembled 链接、旧直接依赖链接 | 生成准确迁移清单；未知来源不自动删除；旧世界数据保留 |
| 与 MCDK/MC Studio 交替或同时使用 | 识别外部链接变化；不误报代码已生效；恢复不清理他人包；未隔离时不承诺并发互不干扰 |
| junction、symlink、真实目录、失效链接、大小写/路径别名/跨盘 | 只改本次拥有的链接；不遍历或删除源目录 |
| 运行中变更声明、显式 reload、多个 watcher | 结构变化先拒绝；内容写入串行；响应未知提示重启、不自动重复执行 |
| Map 自有包与依赖、世界设置、MCS 认证、网络连接 | 原功能不回退，身份凭据不写进部署/恢复日志 |
| macOS 两个实例并行、失败恢复、旧运行包协议 | 实例之间不互相改写；支持边界保持明确 |

自动化分三层：纯状态/选择规则；临时目录加真实锁、junction 和子进程的集成测试；真实游戏测试。故障注入逐个覆盖发布边界，断言源文件、旧产物、链接前像和元数据，不只 mock 返回成功。

真实游戏使用新建临时项目、独立包 UUID 和带版本标记的 client/server 脚本；验证 HUD/world_ready、两端日志/探针、重复启动返回、停止后的文件摘要和保存数据保留。正常退出与异常中断分开测试，不把 Windows stop 的进程退出当作新增的存档保存保证。测试最后仅清理该测试登记的链接/进程，保留失败现场供诊断。

发布条件：状态转换矩阵及兼容性审查中的旧新对照通过；Windows 实机闭环完成；macOS 实机验证后才能声称双平台事务一致；旧入口扫描确认没有绕过协调器的运行目录写入；文档与技能明确实例/会话/部署以及 `--new` 的语义。不能以修改测试预期、默认禁止旧功能或隐藏工作流变化取得“通过”。无法无损保留的行为必须先明确产品取舍。

本轮调研支持固定部署入口和真实跨进程锁，但同时否定了“原有 builder + 单会话限制”的直接替换。下一步先完成 P0 兼容性与真实引擎原型，解决多实例热更和编辑器写回的未决边界，再按 P1–P4 替换生产链路；不以放宽 UUID 校验作为临时修复。
