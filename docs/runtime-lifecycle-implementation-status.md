更新：2026-10-16。此功能仍在开发与实机验收中，尚未达到双平台本地主客机发布门槛。

最新范围调整：按用户要求暂缓 macOS 本地菜单。[第一轮复核](runtime-lifecycle-audit-20261016.md)修复四处启动恢复问题；[第二轮复核](runtime-lifecycle-audit-round2-20261016.md)继续修正创建失败、取消、停止身份交接、外部改动保护和依赖输入变化等组合场景。正式入口导入失败已定位为隔离资料路径与引擎固定截取规则不兼容；改正测试路径后，Windows 的依赖 `0 → 1 → 0`、同版双世界、无变化复用已完成双端正式 Mod 初始化验收。联调组客机的实际业务入口及资源缓存同步仍需独立验收，不能用此前临时注入模块的三端热更结果替代。

## 已取得的实机证据

- 2026-10-16 补充：Windows 同引擎 MCDK 对照已取得本地主客机成功路径。mcpywrap 主机先就绪，原版 MCDK Sub 使用独立资料目录，通过游戏内局域网卡片加入；主机服务端及客户端确认两名不同玩家，客机菜单也列出双方，服务端位置变更同步到客机画面。客机实际使用自身 `packcache`。详见 [同引擎实测记录](mcdk-windows-lan-comparison.md)。这是手工游戏入口的可行性验证，自动 `run --clients 2`、客机 Python 与协调热更尚未因此通过。

- Windows 3.10.0.420447：公开 CLI 启动两个匿名客户端进入同一隔离测试服务器；两个成员均进入世界，并能识别对方。玩家 1 前移约 3.24 格，玩家 2 观察到的位置误差约 0.002 格。
- Windows 第二成员单独重启后，第一成员的会话和进程保持不变；第二成员获得新会话，服务端记录的登录 UUID 保持不变，组再次通过连接验证。
- Apple Silicon macOS 26.6.2 / 开发引擎 3.10.100.299889：身份协议候选运行包通过同样的进服、玩家辨认和位置同步验证；公开组重启返回 `ready`。随后新增的按角色保留资料目录还需再次实机回归。
- 两个平台均观察到服务端把各客户端的本地玩家实体 ID 映射为 `1`。因此连接验证使用各视图的玩家名称映射；本地组还须由主机服务端确认，不能直接跨进程比较实体 ID。
- Windows 仅修改昵称和 `player_info.user_id` 无法隔离登录 UUID。服务端确实记录了重复登录踢出。使用仅作用于游戏子进程的 `USERPROFILE`、`APPDATA`、`LOCALAPPDATA` 后，系统目录 API 指向独立目录，游戏在各成员目录生成了独立身份文件，双客户端进服随之通过。
- 新的资料目录只继承已有画面和输入偏好，不复制账号、设备身份或世界数据；成员重启复用该角色的资料目录，日志和控制通道仍按新会话保存。

## 已落实的结构

本地主客机入口已按产品规则改为手动卡片加入：删除 `runtime/multiplayer.py` 的端口/RakNet 探测与本地自动连接分支，Windows 菜单客机不带 cppconfig，使用稳定角色资料。公开 CLI 返回 `waiting_for_join` 与目标世界提示，不等待用户点击超时；第二成员 worker 持有组监控，核验主机标识和玩家名单。监控在锁外读取游戏，提交时确认组记录未变化，避免阻塞用户操作或覆盖重启后的成员。UI 使用同一状态，未确认加入时禁用组热更。

Windows 产品路径已实测：公开 `run --clients 2` → 用户点击卡片 → worker 自动确认 `ready`；主机客户端、主机服务端与客机客户端 Python 均可执行，组 `both` 热更后三端读取到更新标记。刻意缺少客机模块时，主机完成、客机失败，组返回 `partial` 和非零退出码。单独停止和重试客机保留主机及世界，新会话沿用原角色资料；最后组停止按客机、主机顺序完成。证据位于 `test/mcdk-lan-20261016/product-*.json` 及其 `mcpy-host` 子目录。测试模块是临时注入的探针，不代表复杂 Mod 初始化、订阅和资源热更已验收。

源码尚未应用不再阻止客机加入当前主机；提示保留当前运行版本，应用变更需明确重启联调组。CLI 按需导入命令，状态查询不预先加载全部构建模块；本机导入采样由约 43 秒降至约 9 秒。非 JSON 的失败输出也保留组 ID、成员会话与各端结果。UI 仅保留一个显式组热更入口，成员 Python 控制台不隐式广播。

客机角色保留身份、偏好和世界；主机部署版本改变时，仅清理已确认归属的客机下载缓存，同版重试复用缓存。该行为已有真实文件测试，尚不替代依赖变化后重新下载并加载的实机验收。组成员不能通过单会话 reload/watch 绕过组协调；组停止和重启串行执行，热更取得操作权后重新读取成员，旧会话重试不会停止已替换的新成员。退出尚未确认时不创建替代客机。

UI 可重新接管等待加入的组；当前选中客机时再次执行双客户端运行，仍使用主机的世界。已停止的组不阻挡新的单客户端运行，切换角色不沿用旧控制句柄。

macOS 原生适配器尚无已验证的本地菜单联机协议，当前在启动本地双客户端前明确报告不支持；原外服连接能力不受此限制。组资源热更明确拒绝未同步的客机缓存，不提供旧的共享目录假设分支。

运行写入集中在 `runtime` 服务层。Addon 无依赖和有依赖均装配到稳定运行目录；世界选择与占用检查先于部署。部署保存文件、配置和链接的恢复信息，拒绝覆盖归属不明或被外部修改的内容。

世界与客户端资料共用按进程身份核验的占用机制。worker 退出但游戏仍存活时，下一次操作继续拒绝占用该资源。普通构建和开发监控不能直接写运行目录；GUI 依赖刷新只解析，编辑器使用独立准备目录。

组协调服务供 CLI 和 Qt 调用。中断清理依据本次调用返回的 `owned_sessions`，不从持久组记录推断操作权限。成员重试保留界面所选角色，并更换对应会话句柄。组热更在发布前重新核验连接及各成员就绪情况。

## 尚未通过的门槛

1. macOS 本地主客机仍未完成。Windows 手动卡片加入、自动连接核验和三端 Python 更新已经验证；本地世界使用 NetherNet，不能把其发现端口当作普通 RakNet 服务器端口。客机最小测试包下载到独立 packcache 已确认，业务资源加载、依赖变化后的缓存更新与资源热更仍需验证。
2. Mac 局域网房间初始化曾报错“找不到本机 IP 地址”。隔离候选运行包已补齐网卡标志、列表长度查询及 Java 地址枚举，修正前 5 个 IPv4 地址被报告为 0 个启用网卡，修正后正确返回 5 个及 200 字节列表长度。但最新的限时菜单探针仍停留在登录失败提示，未出现可操作的局域网卡片菜单，也未生成世界。网络开关与地址枚举修复并不足以证明本地加入已可用。
3. Mac 底层网络句柄探测曾使隔离测试进程崩溃。该探测仅保留为诊断证据，未加入产品路径。后续验证应使用有明确参数和生命周期的引擎包装接口。
   后续已读到真实的 NetherNet 主机标识，但向 `world.join_world` 传入它时仍进入 Legacy signaling，未能证明局域网加入。原生网卡与 Java 接口修改仍属实验补丁，不作为本地主客机已支持的依据。
4. 主机异常退出后的存活客机接管、组外部署读者实测、客机资源同步与重载、Map 共享依赖实机兼容、编辑器保存回源码和完整故障中断恢复仍需完成。Qt 状态、关闭视图保留游戏及目标选择已有行为测试；等待/加入两种视图另做了离屏渲染检查。
5. 尚未发布支持独立开发身份的新 Mac 运行包。CLI 会依据协议能力拒绝旧运行包的双身份请求；现有单客户端路径保留。
