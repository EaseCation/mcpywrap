# 运行部署重构：兼容性与副作用审查

日期：2026-10-15。审查对象为拟议方案，不是已经实现的新功能。本文件记录会阻止方案直接落地的反例；主计划必须同步修订，不能把问题留成发布后的注意事项。

后续 [MCDK 竞品与产品分析](mcdk-product-tradeoffs.md) 补充了场景优先级：保护用户可完成的任务，同时明确冲突写入的边界；同版独立世界、主机/客户端联调、不同版本 A/B 不应视为同一种多开。反例清单仍是验证约束，不意味着默认保留所有无保护的旧实现行为。

## 结论

**“固定装配目录 + 同项目单会话 + 原有 builder”不能作为无损替换直接实施。** 它能解决路径切换，但会收缩并行能力，改变源码直读行为，并把构建器的现有缺陷扩散到原本绕过构建的项目。

固定部署位置、先保护后修改、归属登记和失败恢复仍是正确方向。并发规则、编辑器写回、文件复制语义和热更边界必须先通过下列门槛。当前不能声称“没有副作用”；可以明确哪些问题已复现、哪些由代码证明、哪些还需要原型或实机证明。

## 1. 已复现的文件语义变化

在 Windows 临时项目内直接调用真实 builder，与无依赖时的源码目录比较，结果保存于 `test/deployment-research-20261015/compatibility-results.json`。

| 反例 | 结果 | 影响与处理要求 |
| --- | --- | --- |
| 空 `entities/` 目录 | 装配后消失 | 不能假定“文件相同就等价”；保留需要的目录结构并检查包格式要求。当前实验不证明空目录缺失一定会使游戏启动失败 |
| 合法 JSON 文件 `terrain.soil.json` | 装配后消失 | `should_exclude()` 按绝对路径子串匹配 `.so`；必须改为包内相对路径组件/明确扩展名判断，并验证真实原生文件仍被拒绝 |
| 项目目录名 `project.git-copy` | 普通 `marker.py` 消失 | 过滤规则不应由项目父路径决定；此项是无依赖项目迁移前的阻断缺陷 |
| ASCII Python 脚本 | 首行被添加 UTF-8 编码声明 | 文件字节、堆栈行号、断点位置可能改变。区分既有编码修复与必要性，验证 BOM、现有编码、非 UTF-8 和 Python 2，不能宣称纯复制 |
| 编辑源码中的 JSON | 已装配文件保持原内容 | 原生重载快捷键/引擎重新读文件不能自动看到源码修改；必须有等价同步路径或明确的工作流变更 |
| 在运行目录创建 `runtime-generated.json` | 下次构建被删除 | 运行产物中的非构建文件不能无提示丢失；与游戏生成缓存区分，未知文件/改写应保留恢复副本并报告 |
| `behavior_pack` 改名为 `BehaviorPack_renamed` | 实际部署包路径改变 | 固定外层 assembled 还不够；运行包映射必须稳定，源码路径与运行路径分离 |
| 包内目录 junction | 本机实验中的内容保留 | 只是 junction 的正向样例；不等于 symlink、循环链接、跨盘、macOS 或权限受限情况都通过 |
| manifest 和普通 JSON | 本样例字节保持一致 | 必须继续覆盖单包、双 manifest、非默认目录和依赖覆盖顺序，不能由此推及所有文件 |

以上是文件系统事实。没有启动游戏，因此脚本的具体游戏内影响、源路径访问和运行时写文件习惯仍需专项实机验证。极小样例首次 build 约 0.27 秒，只是观测，不作为大型项目性能依据。

## 2. 必须保留的能力及原方案的风险

| 能力或场景 | 可能的回归/新问题 | 审查后的要求 |
| --- | --- | --- |
| 同项目多个世界并行 | 以单会话限制解决共享目录，直接缩减现有 CLI 可达能力 | 撤回单会话默认规则。先验证无修改地加入同一部署；不同代码并行另做隔离原型 |
| 热更只针对指定会话 | 多会话共用文件时，即使只向一个进程发 reload，另一个进程也可能随后读取新文件 | 指定 session 不能当作文件隔离。多读者时不能静默局部热更；须验证独立部署或明确的共享更新语义 |
| 新增模块/资源后的世界内重载 | 首版只允许修改已有文件会进一步收缩能力 | 不以“新增/删除”一刀切；按包结构变化、可部署内容差异、引擎能力区分，验证既有可用工作流 |
| 无依赖项目直接编辑源码后重读 | 始终复制改变即时可见性 | 普通 run 不隐式重装配是边界；源码同步需求通过统一受控 watch 设计并验证。不能额外启动隐藏 watcher 假装无变化 |
| 编辑器保存回源码 | `EditAddOnPaths` 改为产物，但 `SaveBackAddOnPath/SaveBackMapPath/EditPath` 仍是源码；依赖覆盖可能被保存回主项目 | 独立 editor 目录仅解决文件争用，不证明保存安全。验证原生保存行为与来源映射，禁止无脑复制装配树回源码 |
| 已有 world、创建配方、种子/规则 | 新元数据覆盖手动 cppconfig 编辑；重启把创建参数重新应用于已有存档 | 配方读取保留，既有存档设置优先，world/db 不参与部署回滚；逐字段验证 |
| 默认实例 | 由“最新创建”变成“最近运行成功”，会悄悄切换用户默认世界 | 保留按创建时间选最新的排序，只排除未成功/未验证的失败创建；最近使用不另作默认规则 |
| 复用已运行实例 | 新请求的 engine/auth 参数可能被忽略；用户以为已经重启或换身份 | 对不兼容请求报冲突；匹配才复用，并明确未部署当前源码 |
| 两个项目共享同一个依赖包 | 原逻辑允许相同 UUID 且同规范化源目录复用；单一 project owner 会误判为冲突 | 区分链接发布者与使用者集合，保留相同目标的可证明共享；撤销一个引用不能删除另一个引用 |
| Map 多包及嵌入包 | 强行 Addon 合并改变覆盖顺序/UUID；复制世界会覆盖已有数据库 | 独立 Map 装配适配；保留多包身份与优先顺序，单独验证所有包被移除时清空旧引用 |
| 资源包/行为包单边缺省 | 固定两目录、固定两 UUID 或假设主包提供 manifest 会产生虚构包 | 保留单包能力和已有 manifest 优先规则；包集合变化由计划明确表达 |
| 本地/Git/包依赖与纯开发依赖 | 只哈希顶层 pyproject 会漏掉传递变更；过宽哈希又因 README/工具配置变化拒绝热更 | 指纹覆盖真实装配输入和解析语义；开发环境依赖不误入游戏，锁定 Git 提交不自动升级 |
| 诊断、回放和断点 | 新文件位置改变 `__file__`、相对包外读写、日志中的源码定位 | 包内相对路径保持；源码映射用于诊断；包外路径假设需检测与实机确认，不能靠软链接通回可变源码规避隔离 |
| CLI 启动速度和超时 | always-build、哈希、备份将原先 worker 外开销挪入 30 秒 start 等待 | 分开准备进度、worker 交接超时、游戏启动超时；保持取消可达，不能盲目提高一个全局 timeout |
| world_ready 与默认实例可用性 | HUD 日志缺失、开菜单、旧引擎日志格式变化，可能把正常世界永久判成未成功 | 验证可靠的世界初始化信号与降级诊断；进程存活但就绪未知不能直接当作失败，更不能因标记缺失自动杀游戏或删除世界 |
| 磁盘/大型资源包 | 当前产物+完整暂存+旧备份可能达到数倍空间，macOS 多实例会叠加 | 测量字节和峰值；无变化不重复复制/替换；失败留证据有清理策略，不能无界保留 |
| 文件一致性 | 源码在复制期间变更；只比较 mtime/size 漏掉等长修改和低精度时间戳 | 验证实际输入字节；发生变化应中止或有界重试；不宣称任意外部写入下获得真正全盘快照 |
| 引擎缓存文件 | 严格把运行目录每个新增文件计入内容哈希会将 pyc/缓存当作代码改动，持续 busy | 区分构建清单、引擎已验证缓存、未知改写；不凭宽泛后缀静默删除用户数据 |
| 手动指定 build/dev 输出 | 用户可把 target_dir 指到 `.mcpy/runtime/assembled`，绕过 run 锁 | 所有公开写入工具识别受管路径，必须拒绝直接覆盖或进入同一部署协议；只修改 run 不够 |
| Qt/CLI 复用会话的所有权 | attach 已有会话后关闭窗口误 stop；启动中的 handoff 可能没有 game 字段 | 保留 `owns_session`/`already_running` 语义；不把 starting 记录直接传给要求 game 字典的旧 handoff |
| 网络模式/认证/远端 | 新全局预留错误地阻塞纯连接；事务日志记录 auth.cppconfig 含凭据 | 本地部署只适用于本地世界；身份通过既有私密通道交接，备份和全局表不含凭据 |
| 引擎切换 | 同一全局包目录由多个引擎版本共用，仅按版本加锁仍会冲突 | 锁按实际存储根作用域；会话各自保留 engine，产物兼容性单独判断 |
| MCDK/MC Studio 共存 | MCDK 普通启动源码包含清理全局包目录，可能移除本工具链接；我们的锁不能约束外部工具 | 验证外部修改检测与恢复；强并发隔离须验证独立数据根，不宣称单靠归属表就解决 |
| 多客户端联调 | 将所有进程等同于独立世界，可能阻止客户端加入或重复部署宿主 | 客户端加入单独建模和验收，日志/调试端口独立；mcpywrap connect 与 MCDK Sub 客户端不预设等价 |
| 项目复制/移动/多 checkout | 复制 .runtime 带入相同 level_id/owner，可能指向同一个真实世界 | copy 与 move 分开处理：不按复制来的 ID 接管资源；迁移展示世界与归属映射，避免悄悄换世界或丢历史 |
| 用户升级/降级 CLI | 旧 worker 和旧 CLI 不遵守新锁；新字段被旧版本保存覆盖 | 协议版本校验；活动旧会话不自动接管；新版本不能保证旧二进制永不写，必须披露并检测冲突 |
| 坏记录/被搬走的项目 | 全局表任一损坏导致所有项目永久不能 run | 错误隔离到有关的链接/项目，提供只读诊断与可恢复副本；无法确定归属时只冻结受影响资源 |
| 线程、提权和长操作 | CLI 持锁等 worker、worker 持锁等 helper、stop 等构建锁，可能死锁 | 记录锁顺序；worker 不继承或重复获取互斥；helper 使用同一协议；取消/只读 status 不被长构建锁阻塞 |
| 杀进程、断电和磁盘满 | JSON rename 不等于全事务耐久；进程已启动但 PID 未落盘 | 明确 crash-consistency 范围；发布日志先行、必要 flush、幂等恢复；未知进程占用不可按超时释放 |
| 单世界重复启动 | 不同项目持有同一 level_id 时，仅项目锁阻止不了同时打开相同 db | 世界占用按“实际世界存储路径”判定，跨项目也独占；level_id/项目身份不能替代路径身份 |

## 3. 并发方案必须重新比较

| 方案 | 代码复杂度 | 能力影响 | 当前结论 |
| --- | --- | --- | --- |
| 每项目一套稳定目录，只允许一个活动会话 | 最低 | 明确削减多世界并行 | 不作为默认方案 |
| 每项目一套稳定部署，多个世界共享相同产物 | 适中；占用集合和读写规则 | 可保留同版多实例；不同版本与单实例热更无法自然隔离 | 优先验证的最低方案 |
| 每实例/会话独立目录，但继续使用相同全局目录与 UUID | 看似简单 | 引擎仍按 UUID 选包，目录独立不等于加载隔离 | 不成立，不能采用 |
| 每实例独立引擎数据根，包 UUID 保持不变 | 需平台证明 | 有望保留并行和定向热更；还涉及世界、账户、选项、缓存迁移 | 作为 Windows 引擎原型研究，现有 open_game 未暴露此能力 |
| 给每会话重写包 UUID | 规则复杂 | manifest 依赖、世界包引用、资源与持久化关系可能断裂 | 不以此绕过问题 |

共享同版部署的最低规则：

1. 首次启动部署当前代码。另一个不同世界加入前，验证当前源码/依赖装配结果与活动部署一致；一致则只创建该世界配置和会话引用，**不重装配、不改链接**。
2. 内容已经变化时返回 `deployment_in_use`，不能偷偷给新世界加载旧代码，也不能替换其他世界使用的文件。
3. 第二个世界启动失败只回滚其自己的配置/占用，绝不能回滚第一个世界正在使用的部署。
4. 多个使用者存在时，单会话 reload 的文件副作用必须明确处理；不能悄悄广播代码执行，也不能通过单会话禁用功能伪装成完全兼容。这是方案冻结前的关键决策点。
5. 世界占用始终独占，部署读取可共享；最后一个使用者确认退出后才允许常规换版和清理。源码/依赖一致性之外，还需验证引擎版本兼容及是否有运行时改写。

这比“每项目单会话”多了引用集合，但属于问题本身需要表达的关系，不是任意增加框架层次。若要求保留多实例分别热更，必须先验证独立数据根，不能只调整 Python 层锁。

产品上建议优先保证同版并行和单读者快速迭代，对多读者写入给出可见限制与受影响对象。是否首版就交付共享更新，由实际联调场景验收决定；不能隐瞒限制，也不能将不同版本快照扩展成所有普通用户的默认负担。

## 4. 必须补做的验证，不用假通过代替

按差分方式用同一个 fixture 分别运行旧机制和候选机制，比较输出文件清单、字节、世界 ID/数据、脚本双端标记和公开 CLI 返回。不能把修改旧测试预期视为证明兼容。

- **文件与配置差分**：空目录、过滤、编码、包名、单包、双 manifest、嵌套路径、junction/symlink、主项目覆盖依赖、运行时生成文件；既有 cppconfig 手工字段与存档设置。
- **并发差分**：同项目两个独立世界同版同时运行；只停止其中一个；新世界启动失败；两项目共用相同依赖目标；跨项目指向同一世界；与 watcher/编辑器竞争。必须记录两个实例实际加载的标记，不能只检查两个 PID。
- **开发体验差分**：既有模块修改、Python 双端、UI/粒子热更、新资源后世界重载、外部快捷键、编辑器保存回源码、关闭观察者窗口不退出他人会话。
- **恢复差分**：启动/发布每一步故障；worker 死而游戏活；记录损坏；中断期间其他项目操作。确认只有本事务拥有的对象被恢复，未知内容保留。
- **性能差分**：小项目、多个本地依赖、大纹理包、很多小文件；冷启动/热缓存/无改动重启/单文件热更；记录准备耗时、游戏就绪耗时、写入量、峰值磁盘和失败清理。指标与基线比较后再决定缓存，不虚设已达成的阈值。
- **平台差分**：Windows 当前 3.10 与仍声明支持的 3.9，标准用户 junction 与符号链接路径；macOS 独立实例与旧运行包协议。没有目标平台实测就标注未验证。

## 5. 通过标准与当前状态

确定的文件丢失/路径变化反例必须修复并固化为回归测试；公开功能的保留必须有旧新对照证据。无法同时保留的行为单独作为产品取舍，不能偷偷降低功能来让测试通过。

目前完成源码审查、两组 Windows 文件系统/子进程探针及两批现有测试：第一批 53 项全部通过；扩展批 123 项中 122 通过、1 失败。扩展批覆盖 `test_resource_reload`、`test_engine_backends`、`test_qt_sessions`、`test_local_auth_session`、`test_network`、`test_code_libraries`、`test_package`、`test_dependency_boundaries`、`test_engine_discovery`。两批共 176 个不同测试，原环境 175 通过、1 失败。

失败项为 `test_qt_sessions.GuiTests.test_debug_log_displays_regular_output_and_filters_protocol`：fixture 写日志时 `Path.write_text()` 未指定编码，在本机默认编码下生成的中文被 UTF-8 读取后乱码。单独复跑仍失败，使用 `python -X utf8` 单项通过，支持编码环境依赖的判断；未修改测试预期或生产代码。完整扩展批日志在 `test/deployment-research-20261015/compatibility-baseline.log`。这应作为后续编码回归基线处理，不能把有条件通过写成原环境全通过。

**新生命周期尚未实现，未完成游戏内差分验收、编辑器真实保存、多实例隔离和 macOS 验证。** 现有自动化包含 mock，不可当作真实游戏证据。因此方案应先通过兼容性原型阶段，再进入主链路替换。
