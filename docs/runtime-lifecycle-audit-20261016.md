# 运行部署生命周期复核（2026-10-16）

后续更新：[第二轮复核](runtime-lifecycle-audit-round2-20261016.md)已定位隔离资料路径导致的 Mod 导入失败，并完成 Windows `0 → 1 → 0`、同版双世界和无变化重启的完整实机验证。本文保留第一轮当时的结果与失败证据。

本轮暂不推进 macOS 本地联机菜单。复核目标是依赖变化后能否继续使用已有世界，以及新增协调机制是否引入错误占用、错误回滚或状态误报。

## 先提出假设，再验证

| 假设 | 验证方式 | 当前结果 |
|---|---|---|
| 首次添加、删除最后一个依赖仍会切换包路径，引发相同 UUID 冲突 | `0 → 1 → 0` 文件装配测试；旧源码链接迁移后再次移除依赖；公开 CLI 实机脚本 | 文件与链接验证通过；实机结果另列 |
| 换依赖或移除传递依赖后，旧文件仍然残留 | 真目录依赖图 `主项目 → common → leaf`，依次移除 leaf、替换 common | 旧依赖独有文件消失，新依赖文件出现 |
| 游戏退出后，旧锁文件会永久阻挡同一世界 | 创建真实子进程并登记游戏身份；退出前拒绝占用，退出后保留锁文件重试 | 退出前阻止、退出后成功，无需删除锁文件 |
| Windows 文件占用导致发布失败后，下一次仍无法运行 | 用不允许删除共享的真实 Windows 目录句柄阻挡替换，再关闭句柄重试 | 首次发布按预期失败，旧文件不变；释放句柄后发布成功 |
| 同版多世界或活动世界遭到新启动隐式覆盖 | 现有读者保护测试、无变化复用测试；实机脚本分别验证相同与不同部署 | 文件级保护已通过；实机结果另列 |
| 链接或目录发布中途失败后遗留半成品；恢复再次失败不能重试 | 第二个新链接创建失败；恢复目录交换再次失败，再重新恢复 | 校验运行文件、链接登记、配置恢复及下一次发布 |
| 失败创建会成为默认最新实例，或 Map 重启覆盖玩家进度 | 成功实例后创建失败实例；Map 移除依赖并重复复制世界模板 | 默认仍选择成功实例；失败实例可显式重试；已有数据库和 level.dat 字节保留 |
| GUI 刷新或编辑器准备会改写活动运行包 | 修改依赖后调用真实解析与编辑器准备，比较运行目录清单 | 运行目录不变；编辑器保存操作本身仍需原生 UI 验收 |
| 就绪提交遇到临时锁竞争会结束健康游戏 | 在 worker 第一次就绪提交时注入 LockBusy，后一次释放 | **复现缺陷，已修复** |
| 拒绝恢复后，外层异常清理仍会修改未经确认的事务 | 构造进程身份尚未落盘的启动事务，通过真实 Windows 启动服务触发拒绝 | **复现缺陷，已修复** |
| worker 消失而游戏存活时，旧状态仍被当作健康会话复用 | 使用真实存活进程身份、缺失 worker 的会话，再执行 run 服务 | **复现缺陷，已修复** |
| 一个损坏的历史 cppconfig 会阻止其他正常实例迁移旧链接 | 在有效归属配置之前放入截断 JSON、空包引用配置，再迁移旧源码链接 | **两平台复现缺陷，已修复**；仅有效配置可提供归属证据 |

自动化用例位于 `tests/test_lifecycle_audit.py`，使用真实临时目录、链接和进程；只在需要控制失败时注入异常。它们不通过匹配提示文案来替代状态和文件断言。

本轮 Windows 88 项定向测试通过（697.281 秒），覆盖最初 12 项审计用例、部署、组操作、worker、认证和网络回归。对应 Mac 源码基线 708 项全量测试通过，27 项按平台跳过，94.641 秒，进程退出码为 0；这不是 Mac 本地菜单验收。最后的损坏配置修复和归属保护补充后，14 项审计用例与 14 项部署用例再次通过：Windows 28 项 / 49.211 秒；Mac 28 项 / 2.966 秒（1 项 Windows 专属用例跳过）。源码编译与差异格式检查通过。

## 本轮修复

1. worker 将部署锁暂时繁忙视为可重试的提交条件。即使后端只发出一次世界就绪通知，后续轮询仍会完成提交，不再结束游戏；成功实例记录只写一次。
2. 部署恢复先验证归属、占用和启动阶段，验证通过后才接管事务。被拒绝的恢复记录不会进入本次启动的异常回滚范围。
3. Windows 复用实例前重新读取并核验会话。worker 失效但游戏仍存活时，保留占用并返回明确的恢复错误及目标会话，避免假成功；确认停止后才能重启。
4. 旧链接迁移跳过损坏或结构无效的无关实例配置，不修改这些文件，不以它们证明归属。补充同 UUID 跨项目拒绝和链接迁移期间的活动读者保护。

原有“仍有游戏使用则拒绝改写”“同 UUID 的未知外部包不自动删除”继续保留。这些明确拒绝是保护边界，不属于退出后残留锁导致的错误阻挡。

## 实机验证与限制

`tests/manual/lifecycle_dependency_audit.py` 通过公开 CLI 创建隔离项目，依次验证无依赖启动、运行中加依赖、同世界复用、新世界拒绝改写、退出后应用依赖、同版两个独立世界、移除最后一个依赖、再次启动及无变化复用。客户端与服务端分别回读正式 Mod 初始化产生的加载标记；不在探针里伪造模块或加载成功。

前两次首次启动实验分别保留在 `test/dependency-lifecycle-audit-20261016-run2`、`-run3`。它们未在 180 秒内确认进入世界，已清理本任务游戏；不得计为通过。观察到本机可用内存一度约 0.7 GB，以及引擎持续首次资源初始化。内存压力可能影响耗时，但不足以单独证明超时根因；不是通过清理全局链接或删锁解决的。

随后使用上一轮成功运行的隔离资料目录作对照，响应与日志记录在 `test/dependency-lifecycle-audit-20261016-established`。测试仅停止自己项目内的会话，不操作其他项目游戏。

该对照最终进入世界，用户与 worker 的就绪记录一致，证明此前超时不能简单解释为部署锁死。但正式脚本入口未通过验收：引擎自动导入 `com.netease.behavior_packs.<链接名>.AuditMain.modMain` 报 ImportError，调试通道按短模块名导入成功却没有初始化标记。因此尚未完成后续 `0 → 1 → 0` 实机步骤。

后续对照保存在 `test/dependency-lifecycle-audit-20261016-template`：

- 使用与项目生成器一致的 Python 2 旧式类声明，仍未自动加载。探针只读取 `sys.modules`，不手动导入业务入口，结果为空。
- 同一世界、同一脚本改用 MCDK 的 UUID 目录命名，仍发生相同 ImportError。因此不能归因于项目目录名前缀；此候选命名改动已撤回，没有留在产品中。
- 游戏的模块搜索路径包含行为包根目录及选定行为包目录；尚未证明自动生成的模块名为何含有 `com.netease.behavior_packs` 前缀。不能将该问题断言为本轮新增，也不能因为手动 Python 通道可用就忽略它。
- 本轮实验游戏均由验收脚本明确停止，世界和失败日志保留。完整依赖增删实机验收被该正式入口加载问题阻断。

因此本轮结论分为两层：**原有路径切换、旧链接及正常退出后的残留占用问题，已经取得文件级与进程级证据；端到端“重新运行后 Mod 正常生效”尚未通过本轮实机验收，不能宣称整个生命周期已无副作用。**

仍需区分：自动化测试能验证协调器的状态转换和文件恢复；实际世界就绪、业务代码加载、编辑器保存和引擎自身报错必须单独记录实机证据。macOS 菜单和组资源热更不纳入本轮完成声明。
