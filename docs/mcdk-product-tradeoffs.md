# MCDK 竞品分析与 mcpywrap 运行部署的产品取舍

调研日期：2026-10-15。结论用于调整重构优先级，不代表新功能已实现。

## 1. 产品结论

建议把 mcpywrap 的核心承诺定为：**保留测试世界，以当前项目和依赖快速迭代；清楚告诉用户哪些代码已生效，出错后能够继续工作。**

MCDK 最值得借鉴的是短开发循环：在 IDE 启动、修改代码、切回游戏、查看结果，工具负责其间的调试连接和刷新。mcpywrap 的依赖组合、跨平台、可定位会话和自动化验证能力，应当服务于这个循环。部署元数据、锁和事务不应成为用户每次运行必须理解的新概念。

本次不应把“为每个世界保存一套永久历史代码”作为默认能力，也不应为简化实现禁止所有多开。需要区分“同版多世界”“一主机多客户端”“不同代码版本对照”三种任务，并分别承诺支持范围。

兼容性应按用户任务衡量：继续编辑并验证、继续旧存档、多人联调、使用共享库、从失败中恢复。旧实现允许的“另一个启动悄悄覆盖运行包”“删依赖后仍加载旧包”不值得保留；新的行为边界必须明确可见，不能用禁用功能或改测试预期来掩盖退化。

## 2. 调研对象与证据范围

- 核心工具：GitHub-Zero123/MCDevTool，即 `mcdk.exe`。GitHub 最新 release 为 **v1.6.1，2026-09-15 发布**；本轮阅读 main 的固定提交 `d7b6e296653cdf06a66290439d66dbcaa5120405`。[S1][S2]
- IDE 入口：Dofes/mcdev-tools，固定提交 `a31d4a4514593c78745dded5cad19eab0d87fb4b`；独立维护的 VS Code 插件，不把插件能力误归为核心 CLI 已有的所有能力。[S3]
- 生态说明：MCDK-ASSISTANT 是文档/项目分析等 MCP 能力层，不是 mcdk 游戏启动器；社区 `mcdk-macOS` 是另一个项目，不能由其存在推定主线跨平台等价。[S9][S10]
- 方法：阅读公开 README、release、启动/挂载/热更/配置/地图源码及插件多客户端启动代码。下载源码仅用于阅读，没有运行第三方二进制、修改真实全局包目录或测量 MCDK 的游戏性能。
- 上述方法描述的是 10 月 15 日静态调研。10 月 16 日另在隔离数据根运行上游 MCDK v1.6.1 做同引擎对照，成功完成 mcpywrap 主机与独立资料 Sub 的本地入场及位置同步；具体条件和未通过的原始组合见 [实测记录](mcdk-windows-lan-comparison.md)。
- 核对 v1.6.1 与 main：本次关注的 application 启动、配置、地图部署、底层热更文件没有差异；`src/env.cpp` 的差异为 junction 删除语义注释。不能因此把其他 main 新增功能都视为已发布。

文档声明用于判断承诺，源码用于判断机制，两者都不能替代本机游戏验收。以下场景优先级是基于工具定位和本项目已有问题的产品判断，尚无用户使用频率统计或访谈数据支持，不虚构市场份额、性能优势或“多数用户”结论。

## 3. MCDK 提供了怎样的开发体验

| 维度 | MCDK 的公开事实 | 对 mcpywrap 的启示 |
| --- | --- | --- |
| 启动入口 | 插件支持 Ctrl+F5 测试、F5 启动并附加 Python 调试器；自动发现 ModPC，提供可视化配置面板 [S3] | 日常路径应当一次启动即可继续开发，不要求用户先 build、清链接、修 UUID、挑配置 |
| 代码反馈 | 默认启用 Python 自动热更，源码变更后回到游戏前台触发；UI/Shader/Material/Particle 自动热更分别可选，默认关闭 [S1][S6] | 高频脚本反馈应轻便；风险和能力不同的资源更新不应被一个“自动热更”开关混为一谈 |
| 文件加载 | 按目录列表发现包，把源码包 junction 到全局行为包/资源包目录；运行目录命名使用包 UUID [S4][S5] | 它的源码即时可见性来自直接挂载，不能从体验相似推断装配式方案天然等价 |
| 模组组合 | `included_mod_dirs`，每项可设 enabled/hot_reload；启动链为多包挂载 [S6] | 用户关心选择哪些内容参与运行。mcpywrap 还有依赖解析、锁定及同命名空间合并任务，本轮未找到 MCDK 等价的启动装配流程，不能照搬目录挂载替代依赖模型 |
| 世界保留 | `world_folder_name` 选择世界，`reset_world=false` 默认保留；地图开发文档建议按需 reset 重新复制源地图 [S1][S4][S7] | “重新部署代码”和“重置世界”必须分开；持续测试进度与从干净场景验证都要有明确路径 |
| 多客户端 | 文档给出 subprocess 模式用于联机调试；插件分配调试端口，有游戏运行时可启动 Sub 客户端 [S1][S3] | 多开的高价值任务包含主机/客户端联调，不等同于开两个独立世界，更不是两个依赖版本 |
| AI 验证 | MCP 查询日志、双端执行、UI 分析、截图和输入；测试规范强调业务测试入口与结构化日志 [S1][S8] | “已启动”“已进世界”“Mod 验证成功”应可分别观察；重构不能只有 PID 级成功 |
| 运行状态 | 插件可重附加已有调试会话；核心 MCP 随工具/游戏启停，文档说明客户端需要重连 [S1][S3] | 复用、观察、重启和拥有进程的权限应清楚；避免窗口关闭或重连意外终止游戏 |
| 平台 | 核心 README 标记 Windows；存在独立 macOS 社区项目 [S1][S10] | mcpywrap 可保持共同产品语义与平台能力差异，不能为了一个 Windows 限制降低 macOS 已有隔离能力 |

这不是功能数量排名。MCDK 的启动和热更降低了开发者的操作成本；mcpywrap 应重点改善同一条任务链中的依赖一致性、可恢复性及可验证性。

### 必须说明的机制边界

`startGame()` 的普通启动会先调用 `cleanRuntimePacks()`；其实现删除当前全局行为包/资源包目录，然后重新链接当前包。subprocess 分支跳过清理、挂载和创建世界，直接不带世界配置启动游戏。[S4][S5]

### 代码级复核：MCDK 实际怎样完成启动、多开与热更

本轮又按固定提交逐段阅读了本地副本，确认以下链路来自代码，而不是只来自 README 的功能描述。随后完成的同引擎运行对照另见 [MCDK Windows 局域网实测](mcdk-windows-lan-comparison.md)：必须分别判断发现、连接和玩家进入，不能以源码中的 Sub 分支推定联机成功或失败。

**联机结论的边界（2026-10-16 补充）**：下列部署和 Sub 启动机制不能解释或否定游戏自身的局域网加入能力。未发现工具自动加入主机的代码，不等于 MCDK 启动的客户端不能通过游戏菜单加入。需要在同一引擎下对照主机配置、世界联机设置、客机无配置启动和游戏内加入路径，才能定位差异。mcpywrap 此前成功的是两个客户端连接独立测试服务器：Windows 的 `windows-profile-result.log` 和 macOS 的 `network-final-result.json` 均记录 `kind=network`、`connection_verified=true`；这不覆盖第二客户端加入 `run` 创建的本地世界。当前本地入口发现仅识别端口/RakNet，普通 connect 配置使用 `multiplayer_game_type=100`，没有覆盖已观察到的 NetherNet 房间加入路径。这是当前适配范围的缺口，不是本地联机不可行的证据。

1. **运行包是全局 UUID 目录，源码通过 junction 直接暴露。**
   `startGame()` 在普通模式先执行 `MCDevTool::cleanRuntimePacks()`，随后由
   `linkUserConfigModDirs()` 扫描 `included_mod_dirs`。每个包读取 `manifest.json` 的 UUID，目标路径是
   `%APPDATA%/MinecraftPE_Netease/games/com.netease/{behavior_packs,resource_packs}/<uuid>`；
   `createDirectoryJunction(sourceDir, destPath)` 把目标指向源码目录。MCDK 记录的是本次进程内的
   `PackInfo`，没有持久化的项目归属、部署版本或活动读者清单（对应本地
   `src/env.cpp:117-188`、`tools/mcdk/src/mod_register.cpp:49-74`）。内置 Debug Mod 在写入自己的 UUID
   目录前也直接 `remove_all(target)`，没有按链接来源或活动进程做归属校验。

2. **子客户端只避开一次清理，不会获得独立部署快照。**
   VS Code 插件的 `launchNewInstance()` 先通过进程名和可执行文件特征判断是否已有 ModPC；若存在，
   它分配新的 ptvsd 端口并设置 `MCDEV_IS_SUBPROCESS_MODE=1`。核心 `startGame()` 看到该变量后跳过
   `cleanRuntimePacks()`、跳过全局包链接、跳过世界创建和 `dev_config.cppconfig` 写入，直接调用
   `launchGameExe()`。这个设计的价值是“第二个窗口不会马上清空第一个窗口的链接”，但它同时意味着：
   第二个进程读取当前共享数据根中的包，不能代表旧代码组合，也没有由工具自动加入第一个世界的流程。
   插件的会话记录只保存调试端口、工作区和时间；源码中没有世界 ID、玩家角色或组级连接验证。

3. **世界保留和世界重置是一个显式布尔开关。**
   普通模式用 `world_folder_name` 选择固定的运行世界；没有地图源时只在目录不存在或
   `reset_world=true` 时清空并重建 `level.dat`，否则只更新时间戳（插件环境会更新世界设置）。有
   `world_source_path` 时，MCDK 将地图源复制到运行世界；后续默认保留运行世界，只有
   `reset_world=true` 才重新复制。地图的 `behavior_packs`/`resource_packs` 中可识别包会在运行世界内
   建 junction，失败时回退为复制。这里没有把“世界数据”和“代码部署版本”绑定在一起（对应本地
   `tools/mcdk/src/application.cpp:74-129`、`tools/mcdk/src/world_project.cpp:221-288`）。

4. **热更是源目录观察器加 IPC，范围小且不负责部署。**
   启动后 `launchGameExe()` 将参与热更的源目录写进子进程环境，并为 Python、JSON UI、Shader、Material、
   Particle 各自创建观察器。Windows 观察器只订阅 `FILE_NOTIFY_CHANGE_LAST_WRITE`，以 100ms 做防抖；
   Python 变更被转换成包内模块名后批量发送，资源变更发送相应的重载请求。新增、删除和重命名没有进入
   这条监听过滤；JSON 无法解析时会跳过重载并输出诊断。热更触发后由当前 MCDK 进程的 IPC 客户端执行，
   不会重新解析依赖、重新装配运行目录，也没有跨多个 MCDK 进程的协调结果（对应本地
   `src/reload.cpp:59-285`、`tools/mcdk/src/hotreload.cpp:46-240`、`tools/mcdk/src/game_process.cpp:875-976`）。

5. **MCDK 的可观测性强于它的部署隔离。**
   每个 MCDK 进程为自己的游戏进程建立 IPC、日志缓冲和 MCP 服务，并绑定 Minecraft PID；MCP 能区分
   客户端/服务端代码执行和日志来源。插件可以重附加已有调试端口，也能在第二进程上建立新的端口，
   但这属于调试连接管理，不等于世界、部署和玩家会话的生命周期管理。

由此得到的可复用模式是：**启动入口短、每个游戏进程有独立控制通道、脚本热更按变更批量发送、世界重置由用户显式选择**。
不应照搬的部分是：**共享全局目录的先清理后挂载、无归属的 `remove_all`、subprocess 仅跳过清理、以及把
“第二个进程存在”当作多客户端已经联机**。mcpywrap 需要在这些边界上增加部署归属、活动占用、目标角色和
连接验证；同时保留 MCDK 的短路径和按端侧报告结果的体验。

因此：

1. MCDK 的第二客户端流程避开了普通启动的重新部署，给我们提供了“加入现有运行环境不应再次部署”的明确借鉴。
2. 不能据此认定 MCDK 已解决多个独立项目/版本之间的部署归属和事务隔离；本轮阅读的启动链没有给出这项保证。
3. 两种工具默认使用相同的 `%APPDATA%/MinecraftPE_Netease` 数据域。MCDK 普通启动的清理操作可能移除 mcpywrap 的运行链接；mcpywrap 内部的归属表和锁不能阻止不遵守协议的外部程序。这是源码推导的共存风险，未执行破坏性实验。
4. `world_folder_name` 的默认值固定为 `MC_DEV_WORLD`，配置中可更改；不能把默认启动理解为自动创建项目独立世界，也不能由此推定实际用户一定发生碰撞。

对 mcpywrap 的要求是监测外部改写、停止误报成功、给出可恢复的诊断；若承诺两工具同时运行互不干扰，则必须先验证真正的数据根隔离。不能复制“启动前清空全局包”来省掉归属管理。

## 4. 从用户任务定义优先级

下表的“优先级”指本次生命周期重构的范围，不表示某类用户不重要。

| 使用场景 | 用户真正要完成的事 | 必须保留的结果 | 建议优先级与边界 |
| --- | --- | --- | --- |
| 单人脚本迭代 | 改一小段逻辑，立即看效果，保留场景 | 快速、双端可定位、可重复；不用因普通改动重建世界 | **核心**；低操作成本热更与受控同步不能被 always-build 拖慢 |
| UI/粒子/资源调试 | 看清视觉变化，必要时重建界面或重载世界 | 明确刷新粒度与是否生效，不把“请求已发送”当成功 | **核心**；按已验证的引擎能力提供动作，不承诺所有资源无重启 |
| 增删/更换 common 或 QuMod 依赖 | 下次运行准确使用新组合 | 无幽灵依赖，不手工清链接，保留世界 | **核心**；依赖结构变更需要重新运行是合理成本，错误地加载旧版本不可接受 |
| 持久场景测试 | 回到搭好的机器、实体或存档继续验证 | 重新部署不会丢世界进度 | **核心**；源码更新、世界重置、实例删除三者明确区分 |
| 干净初始场景验收 | 从确定起点重复验证初始化/升级 | 不污染工作世界，失败可定位 | **核心**；优先新建临时世界，复用现有 `--new` 语义；地图重新复制是明确的重置动作 |
| 一个主机、多个联机客户端 | 验证同步、权限、不同玩家视角 | 第二客户端不重建主世界、不重部署宿主包、日志/控制绑定正确 | **高价值独立场景**；mcpywrap 已有 connect，但不能声称等价于 MCDK 子客户端发现/加入流程，需专门验证 |
| 同版多个独立世界 | 在不同地形/状态同时对照同一代码 | 可并行，启动第二个世界不动第一个；停止一个不影响其余 | **保留项**；允许共享已验证产物，普通启动只读加入；热更影响范围必须明确 |
| 同项目旧版/新版 A/B | 同时观察不同代码/依赖版本 | 版本真实隔离，两个实例各自读到指定内容 | **明确的后续能力**；当前 Windows 不具备可靠保证，不把 `--new` 包装成快照 |
| 多项目复用同一个 common | 改公共库，分别验证各项目 | 解析结果正确、各项目知晓待部署变化 | **核心一致性**；不因为公共库变化自动改写所有正在运行的项目 |
| 人与 AI 共同开发 | 人保留游戏，AI执行验证并反馈 | 绑定准确会话，行为可追踪，重连不误重启 | **核心**；监控是否开启、更新到哪里、谁可停止都要清楚 |
| MC Studio 编辑器协作 | 美术/配置编辑保存回项目，再进游戏验证 | 改动回到预期源码，依赖内容不被误反写 | **保留项**；独立编辑器输出是技术手段，保存回写通过实机验收才算完成 |
| 日常切换 MCDK 与 mcpywrap | 按任务使用不同工具 | 不丢源码/世界；被外部改变时说明原因和恢复方式 | **基础共存要求**；并发强隔离需数据根原型，不能仅靠内部锁承诺 |
| 跨机器恢复项目/固定版本验收 | 团队成员运行相同依赖组合 | 锁定解析、世界与代码归属可理解 | **保留项**；依赖锁不等于世界快照，运行元数据不能当作可移植项目文件 |

“保存世界”与“历史代码复现”不是绑定需求。用户可以一直使用同一个世界并更新当前代码；需要旧版复现时，还必须指定源码提交、依赖产物、引擎版本和世界基线，不能只保留旧 assembled 文件夹。

## 5. 建议采用的产品规则

### 5.1 默认开发路径保持短

`run` 的默认含义保持为：选择已有可用世界 → 准备当前代码 → 启动或复用匹配的会话。没有变化时复用产物，不重复整树复制。成功输出说明世界、会话、源码是否已部署；正常路径不要求用户处理内部部署 ID。

保留现有显式 `runtime watch/reload`。GUI 可提供“运行并监控”入口或清楚可见的持久化偏好，让日常脚本开发不必每次操作两次；CLI 可随后提供同一动作的组合入口。这里描述的是产品动作，不是宣布已经存在新参数。

监控开启必须可见且可停止；脚本/自动化调用不因是否有 TTY、切换窗口或重连而暗中改变更新策略。MCDK 的“回前台更新”可作为人工交互触发方式研究，不能成为跨平台/远程执行正确性的唯一依赖。

### 典型操作应得到什么反馈

| 用户动作 | 推荐反馈与下一步 |
| --- | --- |
| 游戏已退出，移除最后一个依赖后 run | 自动准备当前代码，继续原世界；不出现手工清链接步骤 |
| 游戏运行时移除依赖，再次 run 同一世界 | 找回原会话，同时明确“当前依赖变化尚未应用，需要保存退出后重新运行”；不能只返回“已运行”让人误以为新代码生效。JSON 同样明确源码与部署是否一致 |
| 开着世界 A，未改代码时创建世界 B | 创建 B 并加入相同代码版本，不改 A 的运行包 |
| 开着 A，改了依赖后尝试创建 B | 说明 A 正在使用当前部署，新的依赖组合尚不能并行部署；保留 A，给出保存退出再启动的路径，不偷偷使用旧代码 |
| 在共享部署上请求只热更 A | 显示 B 也是读者，当前操作不能保证只影响 A；提供已支持的共享更新动作或退出其他读者后的路径，不返回虚假的定向成功 |
| 上次新世界创建失败 | 列出失败原因及可重试实例；成功旧世界仍可继续使用，失败记录不自动抢默认选择 |

这些是交互契约，具体文案和 JSON 字段在实现时统一定义；不要求再增加六种命令或每次弹确认框。

### 5.2 用户只需要理解更新是否生效

使用短状态描述，如“与当前源码一致”“有改动未应用”“依赖变化，需要重新运行”“更新结果未确认”。显示受影响的会话和下一步动作，而不是只给 UUID 或笼统权限错误。

“代码文件已同步”“引擎接受重载”“业务效果已验证”保留机器可读区别；GUI 不必同时展示所有字段，排查时可展开。

依赖结构变化后允许用户先保存退出再 run；不自动终止游戏、不在 remove 时清链接。尝试启动新世界时若要替换活跃部署，给出具体占用会话和操作选项，不能给新世界偷偷加载旧代码。

### 5.3 多开按任务处理，写入按影响范围处理

- 同一世界的重复 run：匹配参数时复用；不同引擎/身份等请求不兼容则明确拒绝，不能忽略参数。
- 同版多个独立世界：保留。加入前核对输入与产物一致，只增加引用，不重装配。世界路径仍独占。
- 联机客户端：加入现有宿主是独立用户动作，不用 `--new` 冒充；加入流程不部署或重置宿主。优先复用现有网络能力，缺少发现/认证/版本支持时如实说明。
- 单会话热更：单独拥有部署时按已验证能力执行。
- 共享产物热更：更新一个文件可能影响所有读者。必须展示并明确选择更新关联会话，或要求退出其他读者后再更新；不能标称“只更新 A”却悄悄改变 B 能读到的文件。
- 多个会话分别热更：只有真正隔离后才承诺。源码联动的共享会话需要统一部署并逐个确认重载；不自动向不属于本次操作的会话广播代码。

建议首个修复版本保留同版多世界启动、完成单读者热更，**对多读者写入实行明确保护**，暂不新增复杂的联调组调度或全量版本库。这确实会限制原先无保护的共享目录热更，必须在升级说明中披露，并先拿用户的实际联调样例验证成本。若该样例表明多读者热更是主工作流，则共享更新或独立数据根必须进入首版门槛，不能用“以后支持”草率发布。

这项建议不等同于限制只有一个游戏进程：世界、联机客户端、调试会话和部署读者是不同对象。保护的是有冲突的写操作。

### 5.4 世界数据与运行版本分别管理

- `--new` 继续表示新世界，默认当前代码；不隐含旧代码快照或复制已有进度。
- 普通重启保留世界；Map 的源世界重新复制应当是可见的重置动作，优先提供新建测试副本，避免默认覆盖工作世界。
- 失败新建可查、可重试，不抢占默认实例；默认排序保留“最新创建的可用实例”，不顺便改变为最近使用。
- 代码、链接和启动配置可以恢复；游戏已写入的世界数据库不宣称被回滚。默认不要以强杀进程换取“事务成功恢复”。

### 5.5 保留简单入口，把复杂度放在工具内

首版不增加“经典/安全/兼容/快照/严格”等大量模式，也不把每次 run 变成确认向导。沿用 run、new、watch、reload、stop 的用户概念；元数据、暂存、归属和恢复只在内部解决。

确需用户选择的只有会改变其目标或丢弃其数据的动作：重置世界、接管归属不明的旧链接、对其他会话应用更新。日常安全迁移和可证明的同项目旧状态更新自动完成，不要求用户反复清目录。

## 6. 取舍判断表

| 决策 | 收益 | 代价 | 建议 |
| --- | --- | --- | --- |
| 所有 Addon 经过同一装配入口 | 依赖数量不再改变运行路径，消除残留文件 | 源码直读体验、过滤/编码语义、耗时改变 | 采用，但必须先修复文件语义缺陷；增量更新和无变化复用是交付条件 |
| 维持依赖结构到重启时更新 | 运行边界可解释，避免混合模块和资源 | 更换依赖后需要保存退出/重新运行 | 接受；优化重启体验，保留世界，明确下一步 |
| 每项目限制单进程 | 实现容易 | 破坏同版对照、联调和旁路客户端 | 不采用 |
| 多世界共享相同部署 | 同版并行成本低 | 热更会产生多读者影响 | 作为最低候选；只读加入、写入显式保护，披露限制 |
| 默认每世界维护永久代码历史 | 易于描述为“完整隔离” | 磁盘、清理、分支/版本认知负担；历史世界可能跑旧代码 | 不作为默认；A/B/复现未来显式提供 |
| 独立引擎数据根 | 隔离不同版本/工具，有望支持定向热更 | 世界迁移、身份、设置、缓存和引擎支持的验证成本 | P0 做可行性原型；若可行且成本可控，可统一作为底层实现，不额外暴露一种运行模式 |
| 运行前全量清理全局包 | 旧链接容易消失 | 影响其他项目、工具和手动包 | 不采用；只更新能证明归属的对象 |
| 全面事务/占用元数据 | 失败可恢复、并发可解释 | 实现和维护成本 | 保留必要的本机发布日志与占用；不扩展为通用工作流/分布式事务系统 |
| 所有功能都等完整隔离后才发布 | 最严格的一次性交付 | 修复依赖删除问题被长期阻塞 | 原型先验证关键场景；分阶段替换，但发布时一条生产写链，已声明能力不得偷偷回退 |

优先级顺序建议为：**不丢数据、不误加载代码 → 常用开发循环顺畅 → 原有受支持场景可继续 → 高级并行/历史复现 → 极端环境优化**。前两项不能相互抵消；热点小修改每次都全量装配也属于产品退化。

## 7. 对重构执行顺序的调整

1. **先用任务样例锁定产品契约**：普通修改、增删最后一个依赖、同版两世界、主机+客户端、编辑器保存、保留世界重启。分别记录现有行为、期望结果与不允许的副作用。
2. **P0 并行度来自实验安排，不增加架构层**：检查文件语义；测小修改和无变化运行成本；验证 Windows 数据根隔离与 MCDK 共存；核验现有 connect 与本机多客户端任务的实际差距。此处是工作安排，不要求引入多套生产实现。
3. **先交付统一部署与恢复**：一条装配和启动链，非活动时安全更新当前代码，失败不污染默认世界；GUI、editor、watch、build/dev 不能绕过写保护。
4. **保留同版加入与单会话快速热更**：用户应能继续多个世界对照。多读者更新的限制必须可见，验收联调样例决定是否把共享更新一同纳入首版。
5. **独立隔离原型若成立，优先用其消除产品限制**：使用同一 lifecycle、backend 和更新服务替换存储布局；不长期保留一套“老启动”与一套“高级启动”。不成立则明确平台边界，不编造环境变量或更改 UUID 来假装解决。
6. **历史复现单独规划**：需要完整的源/依赖/引擎/世界基线定义，不能为此次 bug 修复顺带造一个不完整快照功能。

## 8. 用什么证据判断取舍是否值得

| 任务 | 要记录的指标 | 不可接受的结果 |
| --- | --- | --- |
| 首次启动/无改动重启 | 用户操作数、准备时长、进入世界时长、磁盘写入量 | 要求用户手工清全局包；无变化仍重复写整包 |
| 修改已加载脚本 | 保存到反馈的时间、端侧、手动动作数、实际版本标记 | 每次重启世界；运行文件已更新却报告完成而未重载 |
| 最后一个依赖移除 | 正常 run 是否成功、旧文件/日志标记是否消失 | 旧模块继续加载、UUID 冲突转嫁给用户 |
| 同版两个世界 | 各自加载标记、第二次启动对第一份产物的写入次数 | 第二次启动改写第一实例文件；失败回滚破坏第一实例 |
| 主机+客户端联调 | 加入路径、端口/身份、日志定位、宿主数据和包是否被修改 | 新客户端误触发宿主重置/重部署 |
| 监控与多读者更新 | 可见的目标集合、各会话确认、失败后的版本状态 | 静默更新未选择会话；部分成功却统一显示“成功” |
| 编辑器保存 | 源文件差分、依赖源码差分、再次 run 的结果 | 合并依赖内容反写主项目或保存落在临时目录后丢失 |
| 异常退出/外部工具改写 | 诊断准确度、恢复动作数、世界和源码是否保留 | 误判权限、清掉未知包、无限生成失败实例 |

先测 mcpywrap 旧机制和候选实现的同场景差分；若另做 MCDK 实机对比，固定引擎、资源规模、冷热缓存与测试任务，才比较耗时。MCDK 的“代码直连”与 mcpywrap 的“依赖装配”工作量不同，不做没有控制变量的速度排名。

用户验证重点可收敛为：多开的主要任务是哪一种；脚本与资源更新目前怎样触发；编辑器保存对象在哪里；是否真的需要同时保持两个代码版本；多久改一次依赖；是否交替或同时使用 MCDK/MC Studio。调研结果用于调整范围，不把这些问题当成本轮分析停止的前置条件。

## 9. 对现有计划的修订结论

保留“世界/会话/部署分离”“统一装配”“先检查占用再写”“只更新有归属的链接”“启动失败可恢复”。

调整两点：一是把热更反馈速度和编辑器保存正确性提升为核心验收，不能只证明安全；二是把多开拆成具体任务，保护冲突写入而不是统一限制进程数量。不同版本 A/B 是后续明确功能，联机客户端是应单独验证的高价值工作流。

两份原有技术文档仍作为实现和反例清单；本文件给出产品优先级。最终发布承诺以场景验收为依据，不由“已有某个目录/锁”或“竞品有多开按钮”推定。
